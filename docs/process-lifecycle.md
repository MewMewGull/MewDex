# 执行进程生命周期

本页记录仍需完成的异常退出功能，不是交付验收。正常停止、主进程自然退出、后台进程继续占用目录，以及服务被强制结束，须分别取得证据；前一种成功不能替代后一种。

## 当前实现

`internal/childprocess` 独立于模型协议，统一负责版本探测和长期 stdio 引擎的启动、等待与清理。Windows 使用带 `KILL_ON_JOB_CLOSE` 的未命名 Job；Mac/Linux 为直接子进程建立独立进程组。Mac 执行服务另通过 `internal/serviceguard` 把身份与租约交给独立监护进程。正常路径与异常路径只清理自己登记的范围，不按进程名搜索并结束其他程序。

服务自动启动由 `internal/startup` 处理，业务入口通过 `localnode.Manager.RunManaged` 持有安装租约。Linux 系统服务配置 `KillMode=control-group`；Mac LaunchAgent 的进程组与 `childprocess` 新建的执行进程组不同。系统机制参考 [systemd.kill](https://www.freedesktop.org/software/systemd/man/259/systemd.kill.html) 和 [Apple launchd 手册](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5)。后者说明 job 结束时清理同组进程，不能据此推定新进程组也会被清理。

## 2026-10-29 故障检查

`scripts/managed-exit-risk` 复用正式的启动登记、所有权核对和 `RunManaged` 入口，回调内仅启动有期限的模拟执行进程。它不启动 Codex、模型或共享 Hub。每个模拟进程持有自己的 OS 文件租约；另起无关哨兵进程作为负对照。主进程编号须由 OS 管理器再次确认后，才只对该编号注入 `SIGKILL`。

## 进程身份模块

`internal/processidentity` 已实现独立于 GUI、模型协议和服务启动器的身份基础：使用内核出生编号和不可变的父出生编号确定归属，当前 PPID 改成系统托管者后仍能识别原父子关系。PID 复用不继承所有权；执行新程序只改变执行代次，不改变出生归属。缺失的中间祖先不会按进程名、目录或进程组猜测补齐。身份图有数量上限，按父子边遍历，不反复扫描整张图。

终止接口先复查出生身份和执行代次，再调用系统的 `proc_signal_with_audittoken`，让内核在投递时核对 PID 与执行代次。缺少系统接口时返回不可用，不回退到只按 PID 发信号。绑定使用固定 `purego v0.11.2`，保持 `CGO_ENABLED=0`；仅加载系统 libproc，不安装系统组件或修改全局权限。依据：[Apple 不可变父身份定义](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/proc_internal.h)、[Apple 信号投递实现](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/proc_info.c)、[purego 固定版本](https://github.com/ebitengine/purego/tree/v0.11.2)。

已在实际 Mac `26.6.2` / arm64 / 普通用户下检查：父进程退出后，`setsid` 子进程的当前父编号变为 1，原父出生编号保持；错误出生身份和过期执行代次被拒绝；正确身份可结束目标，另一同用户、同程序的哨兵保留。另有原生检查直接向系统接口提交过期代次，内核返回 `ESRCH`，目标继续运行；正确代次随后结束目标。证据：`.state/process-identity-20261029/native-identity-report.json`、`kernel-tests-v2.log`。源码还通过 PID 复用、重新托管、缺失中间祖先和矛盾快照检查，Windows Go 回归通过。

独立身份检查仅证明这层基础可用。服务异常退出还须接入独立监护并沿真实工具流程检查；快速双重派生、监护丢失和跟踪数量上限不能按单个 PID 消失推断结果。

## 独立监护接入

`RunManaged` 与直接 `serve` 通过 `serviceguard.Run` 共用数据租约，嵌套入口只复用同一数据范围，不能在回调中改用其他目录或新增未受保护的执行。Mac 的同一受信程序以内部 `process-owner` 模式进入自己的会话，继承数据及安装锁的重复文件句柄。原进程关闭句柄不会显式解锁，监护仍持有同一个打开描述；原生 OS 锁检查已证明最后一个继承句柄关闭后才释放租约。

引擎版本探测与长期引擎都使用 `StartContext`。受保护的子进程先进入 `process-child`，只从继承的私有管道读取原执行参数；监护确认出生身份、登记内核事件后才放行 `exec`。不从手机、网络协议或旧 PID 文件取得进程所有权。监护使用 `NOTE_FORK/EXEC/EXIT` 与有界快照追踪，保留已观察到的不可变出生边，`setsid` 和重新托管不会改变归属。

执行前在数据及安装锁目录写入本次关联编号的 `service-ownership.pending`。监护丢失会取消服务上下文；读取失败、数量上限、无法解释的新出生链或清理失败会保留标记。即使所有文件句柄随后关闭，`lifecycle.Acquire` 仍拒绝重新采用这份未核实状态。完成清理只删除匹配本次关联编号的标记，不恢复旧进程编号，也不结束归属未知的进程。后续已补入启动批次来源和本机恢复记录，范围见下一节。

实际启动发现 `/bin/ps` 带 setuid 位，执行时同用户复合信息接口会返回拒绝。现按 XNU 的公开短 BSD 与唯一身份接口，在前后出生身份和执行代次一致时读取其状态；终止接口的权限检查保持不变。依据：[XNU 权限与信息接口实现](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/proc_info.c)、[BSD 字段定义](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/proc_info.h)。前两次失败结果保留为 `failed-native-v1.json`、`failed-native-v2.json`，没有用后续成功覆盖。

## 后续实现要求

独立监护已覆盖两条入口并修复已复现的真实固定引擎脱离会话残留；这仍不是全部 Mac 生命周期已经完成。观察存在数量上限，无法确认的新进程出生链会保守冻结，可能受同机其他快速派生活动影响。有界并发负载与旧记录回收已补入下节；长时间跟踪开销与误冻结、原生恢复界面、真实重新启动、登录和系统回收流程仍待检查。不能把一次有界故障检查推广为所有工具链或系统版本的保证。

清理只能作用于确定属于该安装和执行范围的进程，不能按名称或缓存 PID 扩大终止范围。未核实的停止继续保持未知与冻结，不能把服务主 PID 消失作为全部工作已经停止的证据。现有会话中断、模型任务进程停止与整个服务退出仍须分别处理，不以杀掉共享引擎替代单对话停止。

Mac 缺口、真实引擎故障流程、真实开机/登录生命周期及其他剩余功能完成前，不进入最终打包验证。

## 长期服务的出生记录回收

旧实现按累计观察过的生命周期限制数量，记录只增加、不回收；服务即使已完成全部短任务，累计到 65,536 条也会冻结。现在 `lifetimeHistory` 只限制当前保留的出生链，另用常量大小的累计计数保存观察总量、已回收量和保留峰值。

每次完整扫描先发现后代、分类未知出生链，最后才回收旧记录。只有对应内核观察已结束、持续至少两秒不在完整快照中、没有待核对派生关系和近期出生边的身份才可回收。服务根、仍有内核观察的进程、未核对派生和全部当前进程均保留；已观察的活跃子孙本身继续作为归属根。回收不发送信号，不按缓存 PID 或名称扩大归属；迟到且缺失祖先的未知进程仍使状态保持未确认。

功能检查记录为 `.state/evidence/functional-guard-retention-20261029.json`：

- 身份逻辑在受限保留容量下跨过 65,601 个累计生命周期，已结束记录持续回收；这组为逻辑模拟，没有实际创建同等数量的 OS 进程。活跃子孙与缺失祖先、PID 复用及未核对派生保持检查通过。
- Mac 普通用户实际完成 32 批、8 路并发、共 2,048 个 `/usr/bin/true` 短任务，并等待五秒后检查服务仍存活。监护累计观察 2,016 个生命周期，已回收 2,012 条，最终保留 4 条，保留峰值 552，清理时零剩余、零未核对派生和未知出生链。实际完成任务数与已观察生命周期数分别记录，不声称捕获了每个短命进程。
- 同一源码的正常退出、服务主进程强退、监护强退及刻意缺失中间祖先均完成检查。前两者清理确定范围并释放租约；后两者继续保留冻结，未把未知进程算作已清理。无关哨兵保留，模拟工作负载之后由检查程序自己的停止标记收尾。
- Windows Go 回归、Darwin 静态检查和 Mac 原生定点检查通过。没有更新在线节点、发起官方模型请求、重新启动系统或制作最终候选；这不替代长时间负载、实际登录或开机检查。

## 冻结后的检查记录与恢复

受保护服务现在额外保存本次启动的来源记录，包含关联编号、创建时间和系统提供的启动批次；清理后保留来源文件。Mac 读取 `kern.bootsessionuuid`。Apple 在系统启动时生成该 UUID；代码来源为 [initializeBootSessionUUID](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/Kernel/IOPMrootDomain.cpp)。Linux 的共用接口读取内核 boot_id；无法取得可信启动批次的平台不会编造证明。

Windows 使用 `NtQuerySystemInformation(SystemProcessInformation)` 读取内核 System 进程的固定创建身份，以命名域摘要编码为私有 UUID；不从当前时间或运行时长推算启动时间，也不使用应用进程或登录会话。Microsoft 说明进程创建时间在系统时钟调整后保持不变，参见 [PsGetProcessCreateTimeQuadPart](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/nf-ntddk-psgetprocesscreatetimequadpart)；进程快照接口见 [NtQuerySystemInformation](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntquerysysteminformation)。实现要求唯一的系统进程身份、有效创建值和完整有界快照；读取失败或布局异常时继续拒绝恢复。此次两个独立 Windows 检查进程取得相同身份；真实重启、睡眠、休眠和快速启动的系统行为尚未实测，不能把这些检查算作跨重启验证。

本机面板的“恢复本机服务状态”使用三个操作：`cleanup.status` 读取，`cleanup.prepare` 保存核对记录，`cleanup.apply` 明确采用。采用要求当前设备身份、配置指纹及原冻结标记仍匹配，并持有安装与数据目录的 OS 检查租约。系统仍处于相关任务的原启动批次时拒绝解除冻结。没有启动来源的早期标记先记录当前批次，之后需要一次新的系统重启。输入请求不能提供或覆盖启动批次。

采用前持久化意图，在现有执行数据库中原子保存重启证明和旧执行身份的私有快照，然后分步清除匹配的原标记。快照与本次采用记录一起登记，重试不重新纳入后来出现的任务；当前系统启动批次内提交的新任务不能使用这份旧证明。中断后允许原意图续接，不把无意图的标记消失当作完成。该操作不改写原任务结果、队列输入、配置、模型目录或网络授权，不启动服务、不提交模型输入。面板关闭后从磁盘找回原核对记录；回复丢失时只读回结果，确认完成后同步本机状态，不自动重复操作。早期版本没有执行快照的中断意图仅恢复原有启动限制，不事后补发会话恢复资格。

原会话与队列继续保留待核实结果。服务重新启动后，执行器用私有快照给对应旧执行公布不透明的恢复编号，输入端可明确选择“确认结束旧执行”。它只释放本机项目占用，不调用模型或终止进程；原指令结果、旧回合编号、排队输入与未知结果保持。操作、审计和补传事件同时提交，之后才释放内存中的项目占用；已结束执行在重开后不重新占用项目，迟到模型事件不会覆盖它。旧会话只读，用户显式新建对话继续，原输入不自动复制或提交。

新任务首先持久化新的启动指令编号和系统批次，再调用模型；它不能继承旧证明。只读核实可能发现或清除旧回合编号，因此证明绑定原启动指令而非可变的回合观察状态。结束操作回复丢失时，仅从它自己的持久动作记录恢复控制回执，原模型回执仍保持未知。备份恢复撤销未采用的重启证明与动作授权，保留已结束执行的历史审计，避免恢复旧备份重新打开历史任务。

恢复的执行库可能保留未知任务，却没有服务退出标记。此时本机面板也会显示待核对执行，并允许保存检查记录；尚未经过执行器启动归一化的未知队列同样纳入检查。没有可信原启动来源时，以保存记录时的内核生命周期为界，之后必须确认新的系统重启。运行中的服务只显示原记录和停止提示，不比较暂时变化的服务标记或采用证明；停止后重新取得安装与数据租约，才严格核对当前配置与标记。已经保存的记录在自动启动或关闭工作台之后仍可继续使用。

这条路径仍使用原来的私有重启快照与会话级明确结束操作，不直接解除项目占用。中断在采用意图之前、之后或快照提交之后，均不能把单独的意图文件视为恢复完成。恢复及执行器启动共用未核实状态判断，避免仅有 `stopStatus=unconfirmed` 的记录在重开时失去项目占用。原任务结果和队列保持，结束旧执行后由用户另建对话。
