# 设备数据备份与恢复

## 当前实现

`internal/backup` 独立于 Hub、执行器和图形界面。创建归档与解包分别使用明确的目录、路径、上下文和大小限制；本机管理层选择属于本安装的数据并持有停止状态的数据锁。

本机原生协议的 `backup` 操作接收目的路径和口令，返回设备、时间、文件数和字节数。口令只通过标准输入请求传递，不作为命令行参数、回执、配置或归档元数据保存。备份目的地不能覆盖已有文件，也不能位于本应用的数据目录内。桌面本机设置已接入文件选择、口令输入、恢复方案审阅和重新配对入口。

归档采用固定版本 [age 1.3.2](https://github.com/FiloSottile/age/releases/tag/v1.3.2) 的口令加密，使用 [ScryptRecipient / ScryptIdentity](https://pkg.go.dev/filippo.io/age@v1.3.2)；工作参数为 18，读取时也限制最大工作参数。口令至少 12 个字符。清单、路径和业务数据均在加密流内，清单记录每个文件的字节数和 SHA-256。

默认限制为 64 GiB、100000 个文件和 8 MiB 清单；文件流式读写。解包必须读到加密流末尾并验证认证标签，不能把 tar 的结束标记当作整个加密文件已校验。

## 包含范围

- MewDex 的 Hub / Executor 数据库、Hub 的 `coordinator/coordinator.db`、相关 WAL 文件、附件、设备配置和执行端网络身份。
- 应用自己管理的独立引擎目录中的 `sessions`、`archived_sessions` 对话 rollout 文件。
- 配置中的项目目录引用；项目工作文件仍由原项目仓库或文件备份管理。

备份不读取或打包模型认证文件、系统钥匙串、引擎配置、缓存、运行程序、本地控制记录或锁。使用既有全局模型目录时，不读取该目录；返回结果明确标记是否包含引擎历史。

手动引擎参数、外部代理凭据和 TLS 密钥文件尚未纳入本格式；遇到这些设置会保留原配置并拒绝导出，不静默丢弃设置。普通原生首次配置已支持加密导出。

## 已验证的边界

解包只创建指定父目录中的新子目录，使用 `os.Root` 限定写入范围。格式拒绝路径越界、符号链接、特殊文件、Windows 设备名和数据流、重复路径、大小超限、未声明内容及哈希不符。失败时只清除本次创建的子目录；原有目录和配置不替换。

Windows 与 Mac 的实际 Go 管理程序已完成服务停止后的加密导出和分离解包，原输入身份可从解包的数据库读回。这证明数据归档完整，不代表这些旧身份可以直接在恢复后的网络启用。

固定版真实引擎从解包后的新目录恢复了已有未登录探测的对话历史，原输入编号、回合编号与回执匹配；没有导入模型账号或提交新回合。证据见 `.state/evidence/engine-backup-history.json`。该探测没有切换当前安装的配置。

## 两阶段采用流程

本机管理层已实现以下过程，未提供自动恢复并启动的入口：

1. `restore.prepare` 获取安装级租约与数据锁，解包到新目录，校验业务清单、协议和引擎版本、SQLite 完整性、设备与目录绑定。引擎只能来自原生宿主指定的固定资源。新状态经过迁移、冻结与授权清理后，生成可审阅计划；原配置不变。
2. 计划包含稳定编号、设备、角色、项目，以及重新配对和模型登录需求。调用方可提供自己的固定编号；相同编号和同一密文不会重复准备，不同密文不能占用同一编号。`restore.status` 可观察计划是否已切换，口令不保存在计划中。
3. `restore.apply` 再次检查当前配置、原数据和准备副本的指纹。审阅期间任何相关状态变化都会拒绝切换。确认服务停止后，保留旧配置的原始字节和旧数据目录，最后原子切换配置。重复观察已切换的同一计划不会再次恢复。
4. 恢复的 Hub 身份和配对码全部失效；执行器也不使用归档中的旧节点令牌。`repair.executor` 通过新配对码修复缺失或已被 Hub 拒绝的执行端授权，并保留设备编号与旧凭据文件；目标 Hub 中仍存在的旧设备身份需要管理员先处理。
5. 任务保持冻结，运行或结果未知的任务继续标为未知，旧交互过期。执行端退役旧的待补传状态，启动时重建当前状态快照；原输入与回执证据仍保留。不会因此重发模型输入或恢复队列。

原生服务以 `serve -install-root ...` 持有独立于数据目录的安装租约；停止时需等安装租约与数据锁一起释放。旧的显式 CLI 配置仍可使用原数据锁。缺失或损坏配置的恢复也会检查原数据和保留的恢复目录，不能把控制记录缺失当成已停止。

使用外部全局引擎历史的旧配置只能在原已配置设备上保留该上下文，不能凭不包含历史的归档迁入新的安装。独立引擎目录恢复后需要重新授权模型账号。

Windows 与 Mac 的实际管理程序已完成准备、切换、旧输入凭据拒绝、新输入配对、重新启动及停止；包含固定引擎和 Hub-only 两种探测。证据为 `.state/evidence/local-service-engine-risk-restore.json`、`local-service-risk-restore.json` 及对应 Mac 证据。没有切换正在运行的共享网络配置，没有提交模型回合。

## 后台任务与取消

界面通过 `job.start` 发起加密导出、恢复准备或已审阅方案的切换。调用方先生成固定编号，创建请求只发送一次；`job.status` 通过原编号或本安装最近记录查询，`job.cancel` 请求取消。创建进程退出后，独立工作进程继续运行；关闭、重开界面不重发创建请求。

任务记录只保存非敏感的操作目的与进度，不保存口令或含口令的请求。工作进程通过标准输入取得一次性请求，持有独立租约并执行原有本机管理接口；没有绕过安装租约和数据锁。记录锁短暂争用时查询会等待，而不是把它当作操作失败。

进度按读取、加密、解包、校验、迁移与最终切换等实际阶段报告；只有完整清单可用时显示文件与字节总数，不估算整体完成百分比。取消在流式读写和校验阶段生效；失败或取消只清除本次创建的半成品。进入最终配置切换后，已成功的切换仍返回成功，不因迟到的取消请求显示为取消。

失去工作进程但未得到最终回执的任务保持 `unknown`，同一编号不会再次执行。恢复计划和已原子切换的配置可用于找回成功结果；单独存在的备份文件不能证明导出完成，不会据此宣称成功或自动删除该文件。

Windows 和 Mac 的真实独立进程探测均通过：父进程退出后的观察、同一编号的重复观察、准备与切换、重新配对和启动、备份取消及半成品清理。证据为 `.state/evidence/local-service-risk-restore-jobs.json` 与 `mac-local-service-risk-restore-jobs.json`。首轮 Mac 探测暴露记录锁争用，修正查询等待后通过。定向检查另覆盖读写期间取消、准备恢复期间取消、丢失工作进程不重发和最终切换后的迟到取消。

## 已有执行端重新接入

`repair.executor` 先通过原 Hub 的 `/v1/me` 核对现有身份。有效身份继续沿用，不消耗提交的新配对码；断网、HTTP 403/5xx、设备归属不匹配或请求出口权限不足，都不会据此替换凭据。只有明确的 HTTP 401 或缺失凭据，才允许新的配对。

配对提交前保存一次尝试的编号、设备、Hub 和指纹，不保存原始配对码。收到的新凭据先写入应用目录内受限的待采用记录，重新核对身份后才切换活动文件；被拒绝的原文件按原始字节保留为 `node-token.rejected.<编号>`。此记录属于本地网络凭据，不含模型账号；不放入普通快照、日志或备份归档。

进程在新凭据落盘后中断，可使用空配对码继续核对已保存的结果，不重新提交邀请；活动文件已经切换时也能完成记录清理。响应丢失的尝试保留为待核实，同一配对码不会再次发送。管理员核对成员后，显式提供不同的新配对码才开始另一尝试，原尝试记录仍保留。文件并发修改、运行中的数据锁或目录越界会拒绝切换。

原生本机面板对所有远端执行器提供现有授权检查和重新配对入口。服务启动前再次核对远端授权；已确认拒绝的授权不会直接启动。重新配对不启动服务、不恢复队列，也不改变对话结果。Windows 的真实 Hub 身份清理、原设备重新配对、WebSocket 联机和诊断事件确认均已检查；Linux 相同范围的并发检查通过。证据：`.state/evidence/windows-executor-pairing.json`、`linux-executor-pairing-race.json`。新配对入口的实际原生界面操作仍待检查。

## 后续工作

Windows 本机模拟安装已通过实际系统文件选择器和口令表单生成加密备份，再经解密准备、审阅和采用切换到独立恢复目录；关闭重开后找回同一成功结果，没有再发起任务。设备和项目保持，旧配置及数据目录保留，新模型目录为空，模拟会话冻结且命令为零。实际界面记录与文件/数据库读回见 `.state/desktop-functional-20261029/`、`.state/evidence/desktop-restore-reopened-20261029.json`。同一面板的恢复与升级审阅状态已改为互斥，实际按编号查询互换已通过，避免同时显示不同授权说明。

检查工具也必须保持审阅副本不变。第一份方案被拒绝的原因是 SQLite 只读观察仍生成了 WAL/SHM 旁文件；失败记录和原方案保留。观察脚本已改为在独立证据目录复制停止状态的数据库及 WAL，仅打开这些副本，并比较暂存目录前后的完整清单；第二份方案实际采用成功。

恢复结果已按主控网络和远端执行端分别说明后续步骤；概览与配对页复用同一组服务操作，执行授权完成后可在原页启动，服务就绪后继续输入端连接。此批仍是源码，记录为 `.state/evidence/functional-windows-recovery-flow-20261030.json`，没有实际修改运行中的配对或服务。

恢复后重新配对、取消操作的原生界面流程，以及其他平台的同等界面接入仍需集中联调；后端进程检查不能替代这些界面证据。真实登录/开机生命周期和生产分发也仍待完成。先完成全部功能，再开展最终打包验证。

未知旧执行可能保留项目占用，而模型历史本来就不在备份中。对此，本机面板在没有服务退出标记时也提供检查记录：保存记录，重新启动电脑；如服务已自动运行，先停止，再核对同一记录并明确确认恢复。之后启动服务，在原对话明确结束旧执行，再另建对话继续。原结果仍保持未知，队列输入不自动复制或发送。Windows 原生面板已通过无模型安装的保存、重开和停止模拟服务流程，同次启动内仍拒绝采用；真实跨重启步骤待实际检查。依据与限制见 [进程恢复](process-lifecycle.md)。

## 恢复后的历史附件

输入视图是派生数据，不直接备份。执行器在恢复或重启后的首个新回合，按已确认送达的 `message.user`、完成的 start/steer 回执以及有原生回合编号的队列记录重建附件索引。未发送上传、未派发队列和没有送达证据的未知命令不进入索引。

索引绑定原设备、项目与会话，包含附件编号、名称、媒体类型、大小、摘要及当前路径。每个附件重新核对目标和内容，只放入该会话的只读输入视图；失效、损坏或其他项目的附件会阻止提交新回合。索引按内容摘要命名，不覆盖已变化文件，也不按历史消息中的任意路径读取文件。数据库查询和索引重建接受停止上下文。

实际回合指令追加索引位置说明，不改写原用户策略及策略历史。`turn_contexts` 保存本次完整指令、摘要、范围、策略、引擎和回合编号，并区分准备、已提交、拒绝和结果未知。策略来源面板显示已准备的只读附件路径说明。

## 更新当前安装

`upgrade.prepare` 使用当前应用自带的固定组件，在 `upgrades/<编号>` 中复制并校验停止状态的数据。只迁移受支持的数据库和附件；当前设备、网络身份、模型账号目录及项目绑定继续沿用。模型认证文件和系统钥匙串不读取、不复制。执行器副本中的任务冻结，原执行范围需重新绑定，旧交互过期；运行中或未知任务保持未知，不重发输入。Hub 的当前网络授权保留。

`upgrade.apply` 复用恢复的最终核对和原子切换流程，比较当前配置、源数据、副本、程序、引擎清单及网络凭据。审阅后的变化会拒绝切换。旧配置原始字节和旧数据保留；采用成功后可以按同一编号找回结果。取消只清除本次创建且身份未变化的副本。升级不自动启动服务；已登记自动启动需按新配置重新核对。

后台任务支持升级准备、采用、进度、取消及丢失响应后的观察；本机面板已接入方案审阅和编号找回，手机与网页不暴露此接口。当前受支持的历史来源为固定版 `0.162.1` 和已检查的 `0.154.0`，不接受未知或更新的格式；旧版应用准备但尚未采用的执行器恢复方案需使用当前应用重新准备。

旧历史的独立检查只复制了一个自有、未登录探针的 rollout。新引擎恢复后读回原对话、回合和输入编号，原文件摘要保持，未发送模型回合：`.state/evidence/engine-history-migration-0.154-to-0.162.json`。这项证据不等同于新升级界面的完整流程检查。
